## Competition seed and its source

`warehouse/seeds/extent_competed.csv` lists the six codes found in the snapshot: A, B, C, D, F, G. They are the codes of the derived golden values, so the seed agrees with them (tested). `is_competed` is true for A, D and F, false for B, C and G. A null competition code stays null in the fact, with no dimension row.

Source, as `docs/warehouse.md` records it: the codes and labels are the publisher's `extent_competed_code` and `extent_competed` fields, and an audit fails the build when the seed misses a code or changes a label. The meaning of each code is the FPDS-NG Data Element Dictionary, element 10A "Extent Competed", with FAR Part 6 (subparts 6.1 and 6.2) and Part 13. The three labels that open with "NOT" are the three codes marked false.

## Choices for the owner to confirm

1. **Tie direction.** The contract breaks a tie on `transaction_key` without a direction. I took the greatest key as the latest. It changes no value on 2026-11-01: every reporting UEI has one name.
2. **Same rule for the other dimensions.** `dim_recipient`, `dim_sub_agency`, `dim_psc`, `dim_naics` and `dim_competition` take the name on the latest transaction too. No key of the snapshot carries two names, so this is moot today.
3. **Supporting schemas.** `staging.contract_transaction` and `seeds.extent_competed` sit beside `main`, with SQLMesh's own `sqlmesh` and `sqlmesh__*` schemas. `main` holds only the contract. The contract tables are SQLMesh views over materialised tables in the same file.
4. **Dimension types.** The contract types the fact and `is_competed` only. The other dimension columns are VARCHAR, `dim_date.date` is DATE and its fiscal and calendar fields are INTEGER.
5. **`dim_date`** is generated from the fiscal year of the slice, not from the 296 distinct action dates.

## Open questions and notes

1. **SQLMesh analytics.** By default SQLMesh posts anonymous usage events to `analytics.tobikodata.com`. My first CLI runs and Python builds did so before I saw it in the log. The session proxy refused every attempt with 403, so nothing left the container. The project configuration now turns this off (`disable_anonymized_analytics`), the warehouse tests also set `SQLMESH__DISABLE_ANONYMIZED_ANALYTICS=1`, a test checks the setting, and the logs of the final runs show no attempt.
2. **Seed citation not fetched.** The FPDS dictionary and the FAR were cited from knowledge; the session's network does not reach them. Please confirm the edition and link before quoting the mapping elsewhere.
3. **Stale lines in `docs/sources.md`** that my scope did not let me change: the open point "Missing competition code" still says `dim_competition` needs a row for the null code, which this brief rules out; the `action_date` row says it feeds `dim_date.date`, while `dim_date` is generated and the fact's date joins it.
4. **Push allow list.** `.claude/settings.json` allows `git push -u origin s1-` and `s3a-` only. The push of `s2-sqlmesh-models` went through in this session; a later unattended session may need an `s2-` entry.
5. **Auditing outside a plan.** `Context.audit` uses locally cached snapshot versions, so on a copied database it can look for the wrong physical tables. The tests prove the audits through builds instead. S3b should build with `agentic_bi.warehouse.build` and query the views.
6. **Snapshot path in the fingerprint.** The snapshot path is a SQLMesh variable, so a build from a checkout at another path makes new table versions. Harmless here: every database is built where it is used.
7. **Warnings.** The 108 warnings are pydantic deprecation notices from inside SQLMesh. Filtering them would change `pyproject.toml` beyond this brief. The tests set `MAX_FORK_WORKERS=1` so SQLMesh does not fork while DuckDB threads run.
8. **Session setup.** As in S1, the container's git identity was not the maintainer's; I set the maintainer's name and email in the repository's local config. The prompt named the branch `s2-sqlmesh-models`, so that branch is used instead of the session's default branch name.
